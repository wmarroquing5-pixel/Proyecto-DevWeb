# WEB-TRAT-03 — Contratos REST propuestos (no implementados)

Estos contratos son una propuesta para revisar después de aprobar la persistencia de [`DISENO-FINAL.md`](DISENO-FINAL.md). Los endpoints existentes `GET/POST/PUT /api/tratamientos`, `GET /api/diagnosticos` y `POST /api/tratamientos/{id:int}/consumos` **no cambian ahora**. Ningún endpoint de esta página existe en la API actual.

## Convenciones comunes

- JSON camelCase; IDs persistentes (`idDiagnostico`, `idMedicamento`, `idLote`), nunca correlativos visuales. Fechas UTC ISO 8601 en respuesta; el servidor fija las fechas de confirmación. `Cantidad*Unidades` entera positiva en unidad descontable del lote; `dosis` decimal y `unidadDosis` son clínicamente diferentes.
- JWT y autorización dinámica **en backend**. Los módulos `PrescripcionClinica`, `EntregaFarmacia`, `AdministracionClinica`, `HistorialClinicoFarmaco` y `CorreccionClinica` son nombres **propuestos**; no existen asignaciones aprobadas ni se alteran las 67 actuales. Además del permiso, cada operación comprueba usuario activo, médico responsable o farmacéutico/administrador habilitado, paciente/consulta y sucursal. Los roles `Administrador` y `MEDICO` no reciben permiso implícito.
- `Idempotency-Key: <UUID>` obligatorio en POST mutadores. La API normaliza y compara payload+ámbito con SHA-256 persistente; misma clave y contenido retorna el recurso confirmado con `200` y `Location`, clave reutilizada con distinto contenido `409`. La operación inicial devuelve `201` con `Location`. La comprobación de claves también valida que el usuario pueda **consultar** el recurso antes de devolverlo.
- Errores mediante ProblemDetails: `400`/`422` por datos inválidos, `401` sin sesión, `403` sin permiso/ámbito, `404` recurso no visible o inexistente, `409` por clave incompatible, estado/saldo/concurrencia o stock insuficiente. La política concreta entre `400` y `422` debe alinearse con el middleware vigente; no filtrar información clínica de otra consulta mediante diferencia entre `403` y `404`.
- GET paginados con `pageNumber/pageSize` y orden estable por `(fechaUtc, id)`, filtrados por ámbito. Proteger frente a N+1; no poner tokens ni datos clínicos sensibles en logs. `If-Match`/versión de recurso puede complementar el bloqueo transaccional, pero no sustituye UNIQUE ni la comprobación de stock.

El DTO de creación de receta debe optar por **vincular un `IdTratamiento` ya creado** o crear tratamiento y receta juntos dentro de la misma transacción. No se debe hacer `POST /tratamientos` seguido de `POST /recetas` como dos commits independientes sin reconciliación: una caída dejaría un tratamiento huérfano. La opción definitiva requiere decisión en [`DECISION.md`](DECISION.md); la tabla expresa el contrato del caso vinculado. En todos los casos `IdTratamiento` debe pertenecer a la consulta y no tener otra receta vigente incompatible.

## Compatibilidad y seguridad del contrato vigente

`POST /api/tratamientos/{id:int}/consumos` conserva el comportamiento de **nueva salida independiente** para tratamientos históricos. Para un tratamiento con cualquier `RecetaClinica`, la futura API debe devolver `409` y dirigir al flujo de entrega/administración; no crear movimiento no vinculable. El `PUT /api/tratamientos/{id}` debe rechazar cambios de lote/cantidad/pauta en tratamientos gobernados y no cambiar la consulta/paciente/médico. Guardar receta no llama al endpoint de consumo.

La autorización de prescribir debe exigir vínculo real del usuario `MEDICO` con `Consulta.IdMedico`, además del permiso; un `Administrador` no puede firmar una receta solo por administrar el sistema. Entrega requiere usuario farmacéutico habilitado y sucursal permitida; administración requiere profesional clínico habilitado; una misma persona puede tener más de una función **solo mediante asignación expresa**. GET de historial respeta mínimo privilegio y acceso por consulta. Los permisos actuales de `Permiso` y las 67 asignaciones no se cambian en esta fase.

La API nunca acepta `idPaciente`, `idMedico`, `idUsuarioResponsable`, fecha de confirmación ni `idMovimiento` desde Angular como autoridad. Se derivan o fijan en servidor. Si una receta pertenece a otro paciente/consulta, los POST deben fallar sin revelar información ajena. El backend calcula saldos; el frontend los muestra y reconsulta tras confirmar. Ningún controlador contiene lógica transaccional de negocio: servicios y DTO con `CancellationToken`, `ProblemDetails` y validaciones C#.
